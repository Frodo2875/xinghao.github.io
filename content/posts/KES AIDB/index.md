2026 年 10 月 30 日，电科金仓正式发布 KES AI 数据库，提出将业务语义理解、库内计算推理以及原生安全管控融入数据库内核。

从技术发展角度看，这是一条值得关注的路线：数据库正在从传统的数据存储与查询系统，向能够直接支撑 AI 应用的数据基础设施演进。

不过，对于正在建设数据库智能运维平台的企业而言，我们更关心一个实际问题：

> **当企业拥有上千台服务器、运行 Oracle、OceanBase、达梦、SQL Server 等多种数据库时，KES AI 的技术思路能否帮助我们降低数据采集和智能诊断的复杂度？**

本文结合 KES AI 发布资料、KingbaseES 技术文档、KEMCC 产品能力，以及企业智能运维架构中的典型难题进行分析。

## 一、KES AI 的核心技术：语义、计算与安全下沉

KES AI 最值得关注的不是增加了多少 AI 功能，而是将原本分散在外部应用中的部分能力下沉到了数据库层。

### 1.1 库内语义：让指标含义可理解

传统数据库知道某个字段是什么类型，却未必知道它在业务中代表什么。

例如 `connection_count` 可能表示当前连接、累计连接，也可能是配置上限。如果缺乏统一语义，大模型即使查询到真实数值，也可能产生错误判断。

KES AI 提出在数据库内部维护表、字段、关系与业务计算口径，通过自动发现、AI 辅助建议和人工确认形成语义定义。

这一方向对运维的启示是：除了统一采集指标名称，更应该统一指标含义、统计口径和关联关系。

### 1.2 库内计算与多模型融合

根据发布资料，KES AI 将 ONNX Runtime 集成至库内，支持通过 SQL 调用 Embedding 等模型，并在数据库内部完成向量生成、索引构建和相似度检索。

金仓现有产品体系还提供 KES Vector、KES TimeSeries 等扩展能力，用于处理向量与时间序列数据。

这里的价值不只是减少外部系统数量，还在于降低数据在多个存储系统之间复制与同步的复杂度。

例如，历史故障案例可以与结构化故障记录关联，从而支持语义相似案例检索。

但需要明确：这些能力并不直接负责远程采集 Oracle、达梦等其他数据库的运行指标。

### 1.3 数据库原生安全

传统 RAG 架构往往需要把数据抽取到外部向量库。当数据被复制到新系统后，权限、脱敏与审计策略也需要重新建立。

KES AI 尝试将 AI 相关数据访问与数据库既有的身份认证、权限和审计体系结合。

这对生产运维非常重要，因为智能运维 Agent 不仅需要知道如何查询数据，还必须受到权限、数据范围和操作行为的严格约束。

但应注意，库内执行向量计算并不意味着所有数据永远不会离开数据库。如果应用将检索结果发送给外部大模型，仍需做好输出控制和数据脱敏。

## 二、从产品生态看，真正接近智能运维的是哪些能力？

研究过程中，需要把几个产品和技术组件分开理解。

| 产品或组件 | 主要定位 | 对智能运维的意义 |
|---|---|---|
| KES AI 数据库 | 库内语义、推理与安全 | 为 AI 访问数据和知识处理提供新思路 |
| KEMCC | 企业级统一管控平台 | 统一纳管、监控告警、API 集成 |
| KES OPS | 集中运维管控一体化平台 | 数据库巡检、性能分析和自动化运维 |
| KWR / KSH | 数据库性能报告与采样能力 | 获取数据库内部性能诊断证据 |
| KES MCP Server | AI 与数据库交互的工具接口 | 连接 Agent，执行受控的数据库查询与分析 |
| KES TimeSeries | 时序数据处理扩展 | 可作为运维指标存储与分析的候选技术 |

从我们的实际项目需求看，**KES AI 提供的理念、KEMCC 提供的管理能力、KWR/KSH 提供的内部数据，以及 MCP 提供的 Agent 工具接口，才是更值得组合研究的部分。**

### 2.1 特别值得关注的 KEMCC

[金仓官网](https://www.kingbase.com.cn/product/details_723_100753.html)明确介绍，KEMCC 可以集中管理金仓及其他主流数据库产品，提供指标监控、告警、诊断和与第三方平台对接的 API。

但官网并未给出足够详细的千台级免 Agent 采集架构与性能测试数据。

因此，它可以作为我们调研统一采集平台的技术参考，但是否满足异构数据库场景，还需要实际验证具体接口和产品版本。

## 三、回到核心问题：上千台服务器到底怎么采？

企业数据库智能运维面临一个很现实的两难局面。

| 采集方案 | 优点 | 局限 |
| --- | --- | --- |
| **方案 A：每台服务器部署 Agent** | 容易获取本地主机数据、进程信息、日志与细粒度指标。 | 当服务器规模达到上千台之后，Agent 安装、升级、配置、权限维护和故障处理都会形成显著管理负担。 |
| **方案 B：完全无 Agent** | 通过数据库远程连接、系统视图或现有监控 API 获取数据，减少服务器端的软件部署。 | 受限于数据库暴露的指标、远程查询成本和网络条件，某些主机级、内核级指标仍然难以获取。 |

KES AI 并没有直接消除这个矛盾。

不过，它的技术思路提示我们：**应该把“数据采集”“指标语义”“智能计算”“安全访问”拆成不同职责，而不是让一个 Agent 同时完成所有任务。**

### 3.1 第一条路径：持续监控使用分布式采集

对于连接数、会话、锁等待、主机资源、实例可用性等常态监控数据，可以采用：

> **已有监控平台 → 区域采集网关 → 统一时序指标库。**

具体设计：

- 优先复用现有 OEM、OCP、DEM、Prometheus 等监控数据，避免重复采集。
- 无法复用的数据库指标，通过远程只读 SQL 或数据库适配接口补充。
- 按网络隔离域部署采集网关，使用分片、限流和故障接管机制管理采集任务。
- 根据监控需求设置不同频率，而不是对所有实例、所有指标都执行高频查询。

这种方式能够减少业务服务器上的新增采集组件，但依然需要验证高并发采集对数据库和网络的影响。

[KES TimeSeries](https://www.kingbase.com.cn/product/details_726_371189.html) 在这里可能成为时序数据底座候选方案，但它解决的是指标入库后的存储、压缩和分析问题，不能代替前端采集器。

### 3.2 第二条路径：异常发生时按需深度取证

常态监控不一定需要获取全部深度数据。

当某个数据库出现锁等待异常、慢 SQL 增多或者连接池耗尽时，再启动针对性的诊断工作流。

例如：

1. 监控平台检测到实例连接数异常。
2. 智能运维 Agent 查询 CMDB，确定实例、主机与业务应用关系。
3. 通过只读数据库接口查询会话、等待事件和活跃 SQL。
4. 结合性能快照、日志和变更记录分析异常发生的时间与关联性。
5. 检索历史故障案例，形成带证据的诊断建议。
6. DBA 审核后再决定是否执行生产变更。

这种方式不需要持续在所有服务器上执行深度诊断查询。

对于 KES 数据库，可以研究 KWR、KSH 等原生性能采样与报告机制；对于 Oracle、OceanBase、达梦，则分别采用受支持的性能视图、诊断接口或现有管理平台。

此时，KES AI 的语义与向量检索思想就能真正发挥作用：让 Agent 不仅能看到异常数字，还能理解指标含义、关联上下文，并找到历史相似案例。

### 3.3 第三条路径：建立统一的运维语义层

这是 KES AI 给我最大的架构启发。

对于异构数据库，真正困难的并不只有数据采集接口不同，还包括相似指标在不同数据库中的定义、采样范围和统计口径不同。

例如：

| 统一运维概念 | 不同数据库可能提供的信息 |
|---|---|
| 连接使用情况 | 当前连接、会话、连接上限 |
| 活动负载 | 活跃会话、执行中请求、事务状态 |
| 等待情况 | 锁等待、I/O 等待、事务阻塞 |
| SQL 性能 | 执行次数、耗时、资源消耗、执行计划 |
| 存储容量 | 实例空间、表空间、数据文件、磁盘容量 |

建议在统一智管中心建立指标语义目录，每个指标至少维护来源、适用数据库、单位、采样口径、采集时间、可信度和相关资产。

再把实例、主机、应用、SQL、告警和变更记录关联起来。

这样，无论底层数据来自哪个数据库或者厂商监控系统，Agent 都可以基于统一的语义上下文分析问题。

需要强调的是：**不同数据库的指标并不是天然等价的。语义映射需要由 DBA 验证，不能仅靠大模型自动生成。**

## 四、为什么不建议直接用 KES AI 替代现有运维采集体系？

### 4.1 数据库产品能力不等于通用主机监控

首先，KES AI 是数据库产品能力，不是通用操作系统监控系统。

库内计算可以处理已经获取的数据，但不能天然获取远程服务器上的 CPU、磁盘 I/O 和内核事件。

### 4.2 异构数据库仍需适配

其次，金仓针对自有数据库的能力不能自动扩展到所有异构数据库。

如果企业同时保留 Oracle、OceanBase、达梦和 SQL Server，就仍然需要不同数据库的指标适配和权限管理。

### 4.3 库内推理仍需评估资源竞争

第三，AI 推理下沉数据库内核也存在资源竞争问题。

对于关键交易数据库，需要评估库内 Embedding、向量索引构建以及复杂检索对 CPU、内存、I/O 和事务响应的影响，不能为了运维智能化影响生产业务。

### 4.4 MCP 工具调用与持续采集职责不同

第四，MCP 是工具调用协议，并非持续数据采集协议。

[KES MCP Server](https://gitee.com/king-db/kes-mcp-server) 可以为 Agent 提供数据库结构查询、SQL 分析和健康检查等能力，但不能因此认为其具备大规模高频指标采集与时序数据传输能力。

在生产环境中，还必须独立实施数据库账号最小权限、操作审批与审计，不能仅凭 MCP 的某个模式名称判断执行安全性。

## 五、建议的企业级落地架构

综合 KES AI、KEMCC 以及成熟可观测系统的思路，建议采用：

**“持续采集 + 按需诊断 + 统一语义 + 受控执行”的双通道架构。**

底层保持现有 Oracle、OceanBase、达梦、SQL Server 等数据库运行环境不变。

采集层复用已有监控系统，并配置少量区域级远程采集网关。对于必须本地获取的指标，保留已有 Agent 或选择性部署轻量组件。

数据层统一存储关键时序指标、资产关系、告警和诊断证据。

语义层负责将异构数据库的原始指标转换成经过验证的通用运维概念。

Agent 层通过受限工具接口查询数据、关联证据并生成诊断报告。

执行层则由独立的权限、审批和工作流机制控制，确保 AI 不能绕过生产变更规则。

KES AI 所体现的库内语义、混合检索与原生安全设计，可作为这套架构中语义层、知识检索层和权限层的重要参考，但这是一种工程借鉴，不代表整套方案是金仓现成产品功能。

## 六、如何验证方案是否真的能管理千台服务器？

我认为应该先做一次 50～100 个实例的小范围 PoC，而不是直接在全网推广。

重点验证四个问题。

### 6.1 采集成本

比较本地 Agent、远程 SQL 和已有监控平台 API 三种路径的部署工作量、权限维护成本和数据库负载影响。

### 6.2 实时性

分别测试 15 秒、30 秒、60 秒采集周期，记录指标新鲜度、P95/P99 延迟、漏采比例和异常情况下的性能退化。

### 6.3 数据完整性

明确哪些指标无 Agent 可以获取，哪些必须本地采集，以及监控数据能否支持后续根因分析。

### 6.4 AI 诊断质量

使用实际历史故障案例回放，评估 Agent 是否能找到正确证据、排除错误根因，并给出经过 DBA 认可的建议。

对于 KES AI 和 KEMCC，还应向厂商进一步确认跨数据库适配清单、采集架构、API 能力、千台级性能数据及内核 AI 功能的资源开销。

## 七、总结

KES AI 数据库的发布，反映了数据库技术的一个重要方向：AI 能力正在从外部应用向数据源头、计算引擎和安全机制下沉。

对企业数据库智能运维来说，我认为有三点特别值得借鉴：

### 采集与理解分离

采集层专注低开销获取数据，语义层负责让数据可理解。

### 常态监控与深度诊断分离

高频数据由成熟采集系统完成，深度诊断通过 Agent 按需触发。

### AI 推理与操作授权分离

AI 可以提供诊断和建议，但生产操作必须经过独立、安全、可审计的执行机制。

最终需要解决的，不是给每一台服务器装上一个更聪明的 Agent，而是让少量可管理的采集节点、已有监控设施、数据库原生诊断能力以及统一语义层协同工作。

**KES AI 值得学习的不是“让数据库自己做所有事情”，而是让数据在接近源头的地方变得更有语义、更容易计算，也更容易受到安全控制。**

这或许才是它对千台级异构数据库智能运维建设最实际的启发。
